# Migration Concerns: Photon Fusion → FishNet + Nakama

**Date:** June 14, 2026
**Ticket:** LAT-148
**Purpose:** Document migration concerns for when we move from Photon Fusion networking to FishNet + Nakama. These are notes, not solutions.

## Current Architecture (Photon Fusion)

```
Photon Fusion (Networking)
├── PhotonRoomManager     → Host/Client, room lifecycle, matchmaking
├── NetworkedInput        → Input capture, replication via Fusion input system
├── AvatarProxy           → State interpolation, NetworkTransform
├── SpawnManager          → Spawn/despawn, spawn point management
└── PhotonVoiceManager    → Vivox voice (optional)
```

**Key Photon Fusion Features Used:**
- `NetworkRunner` — Single entry point for all networking
- `NetworkBehaviour` — Base class for networked components
- Built-in `NetworkTransform` for position/rotation
- Built-in input system for input replication
- Automatic client/server role management
- Scene sync (not used, but available)
- Built-in room matchmaking (Photon Cloud)

## Migration Target

```
FishNet (Networking) + Nakama (Backend)
├── FishNet Manager       → Host/Client, room lifecycle
├── Input System          → Custom input replication
├── Avatar Proxy          → Interpolation, transform sync
├── Spawn Manager         → Spawn/despawn
└── Voice Manager         → Voice (Vivox, WebRTC, or other)
```

**Key FishNet Features:**
- `Server`/`Client` role management via `[Server]`/`[Client]` attributes
- Custom input handling (no built-in input system like Fusion)
- `NetworkTransform` component available
- Room management via custom code or Nakama channels
- Spawn system via `[ClientRpc]` and object pooling

## Migration Concerns

### 1. Input Replication — HIGHEST IMPACT

**Photon Fusion:**
- Built-in `IInputState` interface with automatic serialization
- Fixed-timestep replication handled by Fusion runner
- `RequestInput()` and `ReadInput()` API
- Automatic deduplication and ordering

**FishNet:**
- No built-in input system (unlike Fusion)
- Must implement custom input struct + serialization
- Need to handle fixed-timestep replication manually
- Must implement deduplication and ordering logic
- Estimated effort: **2-3 days** for equivalent functionality

**Migration Approach:**
- Reuse the existing `PlayerInputState` struct
- Wrap with FishNet's `[SyncVar]` or custom serialization
- Implement a fixed-timestep input buffer (similar to Fusion's)
- Consider FishNet's `InputComponent` plugin (if available)

### 2. Spawn/Despawn Flow

**Photon Fusion:**
```csharp
runner.Spawn(prefab, position, rotation, callback, player)
runner.Despawn(networkObject)
```

**FishNet:**
```csharp
Server.Spawn(networkObject)
networkObject.Despawn()
```

**Concerns:**
- FishNet uses object pooling — pre-register all spawnable objects
- Spawn callbacks use `OnStartServer`/`OnStartClient` instead of Fusion's callbacks
- Need to handle spawn authority differently
- Estimated effort: **1-2 days**

### 3. Room Management & Matchmaking

**Photon Fusion:**
- Built-in room creation/joining via `StartGame(StartGameParams)`
- Photon Cloud handles matchmaking, room listing, player limits
- Automatic host election

**FishNet:**
- No built-in room system
- Must implement room creation/joining with Nakama sessions
- Need to handle host election manually
- Estimated effort: **3-5 days**

**Migration Approach:**
- Use Nakama's real-time channels for room sessions
- Implement custom matchmaking using Nakama's storage/leaderboard APIs
- Host election: first client to join becomes host, tracked via Nakama session metadata

### 4. State Replication & Interpolation

**Photon Fusion:**
- `NetworkTransform` handles position/rotation automatically
- Custom state via `NetworkBehaviour` state system
- Automatic interpolation on client side

**FishNet:**
- `NetworkTransform` available but requires configuration
- Custom state via `[SyncVar]` or custom sync methods
- Manual interpolation needed (or use FishNet's built-in interpolation)

**Concerns:**
- FishNet's `NetworkTransform` has different configuration options
- Custom state interpolation requires manual implementation
- Estimated effort: **2-3 days**

### 5. Voice Integration

**Current:** `PhotonVoiceManager` uses Photon Voice (Vivox)
**Migration:** Voice manager is independent of networking layer

**Options:**
- Keep Photon Voice (still works with FishNet — they're separate)
- Switch to WebRTC via `Telepathy` or custom wrapper
- Use Nakama's voice channels (if available in target version)

**Concerns:**
- Photon Voice has its own networking layer — may conflict with FishNet's UDP/TCP
- If Photon Voice uses Photon Cloud, need separate Photon app config
- Estimated effort: **0-1 days** (mostly configuration)

### 6. Player Authentication

**Photon Fusion:**
- Anonymous auth by default, or Photon Cloud auth
- Player identity via `PlayerRef` (auto-generated by Photon)

**FishNet + Nakama:**
- Nakama session tokens for authentication
- Player identity via Nakama `Session.UserId`
- Need to map Nakama user IDs to FishNet client IDs

**Concerns:**
- Authentication flow changes significantly
- Need Nakama server setup
- Session management and token refresh logic
- Estimated effort: **2-3 days**

### 7. Networking Protocol Differences

| Feature | Photon Fusion | FishNet |
|---------|--------------|---------|
| Protocol | Custom (UDP/TCP) | Custom (UDP/TCP) |
| Serialization | Fusion's built-in | FishNet's built-in |
| Reliability | Automatic (per message) | Configurable (per message) |
| Bandwidth | ~10-50 KB/s (varies) | ~10-50 KB/s (varies) |
| NAT Traversal | Photon Cloud relay | STUN/TURN or direct |

**Concerns:**
- Both use custom protocols, so migration is code-level, not protocol-level
- Serialization format will change (need to re-serialize state structs)
- Network reliability settings may differ

## Risk Assessment

### Low Risk
- Voice integration (decoupled from networking)
- Basic spawn/despawn logic
- Scene structure

### Medium Risk
- Input replication (requires careful timing)
- State interpolation (needs tuning)
- Nakama integration (new backend)

### High Risk
- Room matchmaking (no built-in solution)
- Host election and authority transfer
- Network reliability edge cases

## Code Reuse Opportunities

The following components can be migrated with minimal changes:
- `AvatarProxy.cs` — Interpolation logic is networking-agnostic
- `AvatarState` struct — Serialization wrapper can be adapted
- `SpawnManager` — Spawn point management is generic
- UI (`RoomUI.cs`) — Most logic is UI framework, not networking

## Conclusion

The migration from Photon Fusion to FishNet + Nakama is **feasible** but requires **2-3 weeks** of focused effort. The most impactful changes are in the input system (Fusion has a built-in system, FishNet does not) and room matchmaking (FishNet has no built-in solution).

**Recommendation:** Keep Photon Fusion for production launch, migrate to FishNet + Nakama when backend persistence and custom matchmaking become critical requirements.
